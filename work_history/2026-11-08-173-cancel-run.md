## 수행한 변경

- `api/run_store.py`: 상태에 `cancelling`(멈추는 중), `cancelled`(멈춤) 추가. `RunState.cancel_requested` 플래그, `RunStore.request_cancel(run_id)`, `ACTIVE_STATUSES`(`pending`/`running`/`cancelling`) 신규. `record()` 는 `cancelled` 이벤트를 종착 이벤트(SENTINEL)로 다루고, `run_start` 는 `pending` 일 때만 `running` 으로 바꾼다 (취소 요청 뒤 늦게 도착해도 `cancelling` 을 덮어쓰지 않음). `find_active`(#172) 는 `cancelling` 도 도는 중으로 본다.
- `api/runner.py`: `RunCancelled(BaseException)` 신규. 진행 콜백(`graph_progress`)이 노드 이벤트마다 취소 플래그를 보고, 켜져 있으면 이벤트를 기록하지 않고 `RunCancelled` 를 던진다. `work()` 가 이를 받아 `cancelled` 이벤트를 내보낸다 (`save_reports`/`done` 은 호출하지 않음).
- `api/routes/runs.py`: `POST /api/runs/{run_id}/cancel` 신규 — 200 + 현재 `RunSnapshot`, 없는 run 은 404. SSE 스트림은 `cancelled` 에서 닫힌다. 목록의 `status` 필터(#171)에 두 값 추가.
- `tests/test_api_runs.py`: 8건 추가.

## 설계 결정 변경 사항

`code_artifact.md` 와 달라진 지점 없음. 이슈가 "확인하지 못한 것" 으로 남긴 부분과 제안을 아래처럼 정했다.

- **협조적 취소를 진행 콜백에서 던진 예외로 구현.** 분석은 `graph.propagate()` 동기 호출 한 번이라 스레드를 강제로 끊을 수 없다. 그래프는 노드 시작·완료 때마다 같은 스레드에서 `_emit_progress` 를 부르므로 거기서 예외를 던져 `propagate` 밖으로 빠져나온다. `_emit_progress` 가 `Exception` 만 삼키기 때문에 취소 신호를 `BaseException` 으로 했고, 이 결합은 실제 그래프로 단위 테스트(`test_graph_lets_run_cancelled_through_progress_callback`)를 걸어 두었다.
- **LangGraph 동작을 별도 실험으로 확인** (스크래치 스크립트, 저장소에 없음): `A → (B1‖B2) → C → D` 에서 `B1` 결과 이벤트에서 예외를 던지면 `C`, `D` 는 시작하지 않았고 이미 도는 `B2` 는 끝까지 돌았다. 또 스텝 결과 이벤트는 같은 스텝의 병렬 노드가 모두 끝난 뒤에 도착했다. 즉 **취소는 다음 노드 이벤트까지 걸리는 시간만큼 늦고(최대 한 스텝), 이미 도는 모델 호출은 쿼터를 쓴다.** 새 노드는 시작하지 않으므로 "쿼터가 더 나가지 않는다" 는 목표는 그 범위에서 성립한다. 실제 Claude Code 로 취소를 돌려 보지는 않았다.
- **`pending` 도 `cancelled` 로 곧장 바꾸지 않고 `cancelling` 을 거친다.** `pending` 은 그래프 생성 중일 수 있어 스레드가 이미 돌고 있다. 분석 스레드가 첫 이벤트(`run_start`)에서 플래그를 보고 멈추므로 노드는 하나도 돌지 않는다 (테스트로 확인). 이슈 제안("`pending` 이면 `cancelled`")과 달리 한 번 `cancelling` 을 거치는 점만 다르다.
- **`cancelling` 상태 신설.** 요청과 실제 멈춤 사이에 클라이언트가 구별할 값이 필요해서. 종착 상태는 `cancelled`.
- **마지막 노드가 끝난 뒤 도착한 취소는 `done` 으로 끝난다.** 이미 끝난 분석의 결과를 버리지 않는다 ("이미 끝난 분석은 취소할 것이 없다").
- **취소된 분석의 파일:** 상태 로그·보고서 저장은 `propagate` 끝에서 하므로 취소되면 만들어지지 않는다 (체크포인트는 기본 꺼짐, 켜면 기존대로 재개용으로 남는다). 남기거나 지우는 처리를 새로 만들지 않았다.
- `DELETE` 대신 `POST …/cancel` 만 만들었다 (run 기록을 지우지 않으므로).

## 다음 작업 핸드오프

- 한계: 취소는 다음 노드 이벤트에서 효력이 난다. 노드 하나(또는 병렬 스텝 하나)가 오래 걸리면 `cancelling` 이 그만큼 이어진다. 진행 중인 `claude` subprocess 를 직접 끊는 것은 하지 않았다.
- 한계: `run_store` 는 프로세스 메모리라 서버를 다시 켜면 `cancelling` 포함 모든 상태가 사라진다 (#172 와 같은 한계).
- 웹 `RunPanel.tsx` 는 취소 버튼이 없고, 다른 클라이언트가 취소한 run 을 보고 있으면 SSE 의 `cancelled` 이벤트를 몰라 "실행 중" 으로 남을 수 있다. 이번 PR 범위 밖 (후속 이슈 후보).
- krx-screener 는 시간 초과 시 `POST /api/runs/{id}/cancel` 을 부르고 `status` 가 `cancelled` 가 될 때까지 기다리면 된다. `#172` 의 "끝나지 못하고 running 에 남은 분석" 도 이제 취소로 풀 수 있다.
